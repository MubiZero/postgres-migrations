# Expand/contract — безопасное переименование, смена типа, удаление

Корень всех трёх операций один: деплой кода и миграция базы **не атомарны друг относительно
друга**. Между накатом миграции и раскаткой нового кода на все инстансы (rolling deploy, синие/
зелёные среды, просто разное время перезапуска процессов) есть окно, где старая версия
приложения ещё обращается к схеме так, как обращалась раньше. Миграция, которая ломает это
обращение, ломает прод в этом окне — даже если код и миграция оба правильные по отдельности.

Решение — разбить одно концептуальное изменение на несколько независимо безопасных шагов,
каждый из которых можно выкатить и подождать, прежде чем выкатывать следующий.

## Переименование колонки

1. **Expand.** Добавь новую колонку с новым именем (nullable или с константным умолчанием —
   см. `lock-levels.md`, это мгновенно). Не трогай старую.
2. **Двойная запись.** Задеплой код, который пишет **в обе** колонки при каждом изменении, читает
   пока из старой. Это отдельный деплой, без изменений в базе.
3. **Backfill.** Заполни новую колонку из старой для существующих строк, батчами
   (`lock-levels.md`/`SKILL.md` про батчи).
4. **Переключение чтения.** Задеплой код, который читает из новой колонки, продолжает писать в
   обе (откат на предыдущий шаг ещё возможен, если что-то не так).
5. **Остановка двойной записи.** Задеплой код, который пишет только в новую.
6. **Contract.** Через безопасное окно после шага 5 (дни, не минуты — должна быть уверенность,
   что откатывать на старый код уже не планируется) удали старую колонку.

Шесть шагов для одного переименования выглядит избыточно для маленького проекта с одним
инстансом и мгновенным деплоем — тогда риск окна несовместимости меньше, но он не нулевой
(читающий реплика, фоновый воркер со своим циклом перезапуска, просто время между `git push` и
рестартом процесса). Решение о том, где упростить до меньшего числа шагов — по `PROFILE.md`
проекта (если ведёт `runway`) или по явному решению владельца, не по умолчанию «у нас всё быстро,
значит можно одним шагом».

## Смена типа колонки

Тот же паттерн с дополнительным шагом конвертации:

1. Expand: добавь колонку нового типа.
2. Backfill: заполни её из старой с конвертацией, батчами.
3. Двойная запись: код пишет в обе, конвертируя на лету.
4. Переключение чтения на новую колонку.
5. Остановка двойной записи.
6. Contract: удали старую колонку нового... то есть старую колонку старого типа.

Не делай это через `ALTER COLUMN ... TYPE` напрямую на таблице с данными, кроме проверенных
совместимых пар типов на используемой версии PostgreSQL (см. `lock-levels.md`) — для всего
остального прямая смена типа означает полную перезапись таблицы под эксклюзивной блокировкой.

## Удаление колонки или таблицы

Удаление — это contract без предшествующего expand: безопасно только когда ничто в
**уже выкаченном** коде (включая код, который ещё может откатиться назад) не читает и не пишет
туда. Проверка перед удалением:

- Грep по кодовой базе на использование — не полагайся на память о том, что «это точно больше
  не используется».
- Фоновые задачи, воркеры, другие сервисы на той же базе (частый случай на общей инфраструктуре
  с несколькими продуктами) — не только основной сервис.
- Окно после полного отказа от использования — то же самое «дни, не минуты», что и в
  переименовании: откат на предыдущий релиз не должен внезапно упереться в удалённую колонку.

## Что не нужно разбивать

Expand/contract — цена за совместимость во время раскатки, не ритуал для каждой миграции.
Операции из раздела «Безопасно» в `lock-levels.md` (добавление nullable-колонки, добавление
constraint через `NOT VALID`) не нуждаются в многошаговом паттерне сами по себе — только когда
они часть более крупного изменения (переименования, смены типа), которое действительно создаёт
окно несовместимости.
